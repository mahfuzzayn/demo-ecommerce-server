# Taste
- Prefers using the Codebase Memory MCP tools (index_repository, get_architecture, search_graph) for repository exploration and summarization tasks, explicitly requesting them by name. Confidence: 0.7
- Expects new features/modules to strictly follow the project's documented specs and existing code conventions — repeatedly instructs "follow the rules strictly" when kicking off a new module from a spec doc. Confidence: 0.9
- Maintains feature/API specs as markdown docs in the repo (e.g., src/docs/api-routes.md) and expects them to be read (and re-read on request) before implementation begins. Confidence: 0.7
- Expects every module in the project to have a comprehensive readme.md file (overview, how-it-works, and test data with request/response examples), including retroactively adding them to existing older modules that lack documentation. Confidence: 0.8
- Does not want the assistant to run build/compile verification commands automatically after code changes — said "I will build when needed." Confidence: 0.8
- Communicates tersely and directively; expects immediate execution ("start working on X now") without lengthy back-and-forth or planning discussion. Confidence: 0.6
- Proactively considers data flow and parameter transmission across system boundaries (e.g., how data arrives at each endpoint between services/gateways/frontend) before considering a feature complete; asks "how will it be receiving [data X] ensure it" to verify the contract between systems. Confidence: 0.7
- When debugging multi-step integrations where data passes across system boundaries (payment gateways, APIs, webhooks), wants a systematic step-by-step trace from initiation through each stage — "Verify from starting: Init, then ... then redirect, validate etc. step by step" — rather than isolated fixes at individual endpoints. Confidence: 0.7
- When debugging issues that persist after an attempted fix, wants the assistant to first investigate, diagnose, and explain the root cause ("find and tell me that first!") before making further code changes — diagnosis before action. Confidence: 0.8
- Provides IDE-context annotations (`<ide-context>`) with exact file path and line number before making requests, to give precise location context without needing to be asked. Confidence: 0.7
- Is token-cost conscious; when asked to use token-saving approaches (e.g., Codebase Memory MCP), expects a quantified report of estimated tokens saved at the end of the task. Confidence: 0.7
- Prefers image/file uploads to use Cloudinary via multer middleware (`multerUpload.single()`, `parseBody`) rather than accepting raw URL strings in the request body. When adding upload support to a module, expects validation schemas to exclude fields that will be provided via file upload instead. Confidence: 0.8
- Expects the assistant to implement only what was explicitly asked for — does not want extra routes, handlers, or endpoints added without being requested. Pushes back sharply when assistant introduces unrequested functionality (e.g., separate success/fail/cancel callback routes that were not part of the original requirement). Confidence: 0.9
- Has clear architectural decisions already in mind and expects the assistant to follow that design rather than proposing or implementing alternative approaches. When a single-endpoint pattern (validate + redirect) is already established, all callbacks should flow through that same endpoint rather than being split into separate routes. Confidence: 0.8

- For Stripe integrations, prefers to maintain both PaymentIntent and Checkout Session implementations alongside each other in the codebase ("seperate both and keep both features but activate the checkout system"), keeping one active while the other is preserved for potential future use. Confidence: 0.8

- When a redirect-based payment gateway route pattern (success/cancel callback routes) was previously working and validated, prefers to restore that known-good pattern rather than redesign the integration — "the previous thing ... was working good previously add and make sure validation will work without any issue." Confidence: 0.7
- When implementing payment gateway integrations, expects webhook/callback signature verification to be included from the start — explicitly requests "make sure validate webhook works" as a requirement alongside the main implementation, not as a later add-on. Confidence: 0.6
- When a payment integration uses frontend SDK methods (e.g., Stripe PaymentIntent with confirmCardPayment), prefers the backend as a pure JSON API layer without redirect callback routes. However, when using a redirect-based gateway (e.g., Stripe Checkout Sessions, SSLCommerz), expects dedicated server-side success/cancel callback routes to handle the gateway redirect and forward the user to the frontend. Preference is integration-model-dependent, not absolute. Confidence: 0.6
